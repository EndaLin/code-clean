# Java 集合与并发

## 集合契约

- `[强]` 判断集合为空使用 `isEmpty()`；传给 `addAll` 等不接受空引用的方法前明确处理 `null` 契约。
- `[强]` `Collectors.toMap` 必须明确重复键策略；映射值可能为 `null` 时不要直接依赖 `toMap`/`Map.merge`。
- `[强]` `subList` 是原列表视图，不能强转为 `ArrayList`；父列表结构变化可能使视图操作失败。需要独立副本时显式复制。
- `[强]` `Map.keySet/values/entrySet` 是视图，不能假设支持添加；`List.of`、`Collections.emptyList` 等不可变集合不能修改；`Arrays.asList` 长度固定且与原数组共享元素。
- `[融合]` 集合转数组使用带类型的方式，例如 `toArray(String[]::new)` 或兼容目标 JDK 的 `toArray(new String[0])`。
- `[强]` 不在增强 `for` 中直接增删同一集合；使用迭代器、批量方法或构造新集合。并发修改需选择正确的并发集合或同步策略。
- `[强]` `Comparator` 满足反对称、传递和等价一致性，优先组合标准比较器并覆盖相等情况。
- `[强]` 理解 `? extends T` 适合读取、`? super T` 适合写入，不使用原始类型绕过泛型检查。
- `[建议]` 已知规模时设置合理初始容量；未知时采用默认值，不凭猜测过度分配。
- `[建议]` 读取键和值时遍历 `entrySet` 或使用 `forEach`；选择集合前确认顺序、唯一性、排序、空值和线程安全契约。

## 并发设计

- `[融合]` 先把并发代码与业务逻辑分离，尽量减少共享可变状态；线程安全必须覆盖对象及其方法的完整不变量。
- `[强]` 平台线程池使用有意义的线程名、明确的最大并发、队列容量、拒绝策略和关闭策略，避免无界队列或无限创建线程。
- `[融合]` 不机械禁止所有 `Executors` 工厂。传统固定/缓存池要检查资源上限；现代虚拟线程执行器可用于合适的阻塞任务，但仍需限制下游资源并传播取消和超时。
- `[强]` 在线程池中使用 `ThreadLocal` 后在 `finally` 调用 `remove`；它只隔离线程局部值，不能保护共享对象。
- `[强]` 多个锁保持全局一致的获取顺序；持锁区尽量小，不在其中执行不可控的远程或阻塞调用。
- `[强]` `lock()` 成功后立即进入 `try/finally`；`tryLock()` 只有成功时才解锁，并处理超时与中断。
- `[融合]` `volatile` 只保证可见性和特定有序性，不让复合读改写自动变为原子；计数按争用情况选择原子类、累加器或锁。
- `[融合]` 乐观锁、悲观锁和重试次数由冲突率、幂等性与业务风险决定。使用版本字段防止更新丢失，但不要盲目固定“至少重试三次”。
- `[强]` 定时或异步任务必须捕获并上报任务自身异常，避免单个失败悄然终止后续调度；等待器在 `finally` 中释放计数。
- `[原则]` 明确任务所有权、取消、超时、背压和关闭流程；关闭代码与高负载边界都需要测试。

## 常见误判

- `ConcurrentHashMap` 不接受 `null` 键值；普通 `HashMap` 不是并发容器。
- 线程安全集合不等于跨多个操作的业务不变量自动安全。
- 把整个方法加 `synchronized` 可能正确但代价高；是否缩小锁范围必须以不变量和证据为依据。
- 不因看到并发原语就直接重写；先证明竞态、死锁、饥饿或资源失控的触发路径。
