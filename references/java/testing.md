# Java 测试与安全重构

## 测试应保护行为

- `[融合]` 测试应自动、独立、可重复、自校验并可及时运行；测试代码与生产代码一样需要清晰维护。
- `[原则]` 一个测试聚焦一个行为或概念。可以有多个共同证明该行为的断言，不机械追求“一测试一断言”。
- `[原则]` 测试名称描述场景和结果；准备、执行、断言三个阶段清楚，隐藏与意图无关的搭建细节。
- `[原则]` 覆盖正常路径、边界、失败、回归点和容易被忽视的简单情况。修复缺陷时在附近补充能复现它的测试。
- `[强]` 测试不能依赖执行顺序、共享脏状态、人工输入或不受控的时钟、随机数和网络。
- `[融合]` 单元测试放在项目约定的测试源集；Maven/Gradle 默认通常为 `src/test/java`，多模块或其他构建系统服从实际配置。

## 覆盖率与测试层次

- `[融合]` 覆盖率用于发现未执行区域，不代表断言质量。黄山版的 70%/100% 数字是组织建议，只有项目明确采用时才作为门槛。
- 单元测试验证局部逻辑；集成测试验证数据库、序列化、框架配置和远程边界；端到端测试验证关键用户流程。不要用 mock 通过冒充真实边界已验证。
- 数据库测试自行建立所需数据并清理或回滚，不假设环境已有特定记录。
- 并发测试覆盖取消、超时、关闭、重复执行和竞争边界；避免仅靠固定 `sleep` 推测时序正确。

## 重构保护网

- 修改已有行为前运行相关测试；测试不足时先写特征测试记录当前可观察行为。
- 每个小步后重新运行最接近的测试，最后运行仓库要求的完整检查。
- 不为了让测试容易而暴露内部字段或破坏封装；先提取时钟、存储、远程客户端等真正的边界依赖。
- 测试失败时先判断是需求回归、测试脆弱还是环境问题，不直接改期望值迎合实现。

## 交付证据

报告实际执行的命令类别、测试数量和失败原因。涉及真实数据库、模型、文件、消息或业务 API 时，只有实际命中该系统才能下结论；缺少凭证或系统不可用就明确标为未验证。
