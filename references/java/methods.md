# Java 方法与控制流

## 方法职责

- `[原则]` 一个方法完成一个可描述的职责，并保持单一抽象层级。若必须用“先做 A，然后处理 B，同时还负责 C”描述，通常需要拆分。
- `[原则]` 代码应能自顶向下阅读：公开意图在前，细节下沉到命名清楚的私有方法。
- `[融合]` 方法长度是信号，不是裁决。黄山版建议不超过 80 行；更重要的是职责、分支、抽象层级和可测试性。
- `[原则]` 消除真正的重复知识，但不要把偶然相似的两段代码过早绑定为抽象。
- `[原则]` 方法名说明动作、结果和重要副作用。会修改状态、发送消息或访问远程系统时，不要伪装成普通查询。

## 参数和返回值

- `[原则]` 参数越少越容易理解；零到两个通常最清楚。三个以上先判断它们是否构成一个有名称的概念，再决定是否引入参数对象。
- `[原则]` 避免布尔标志参数，它通常意味着一个方法承担两种行为；若两种调用意图不同，使用两个命名明确的方法。
- `[原则]` 避免输出参数。返回结果或修改接收对象通常更符合读者预期。
- `[强]` 可变参数只承载同类型、同业务含义的数据，避免 `Object...`，并放在参数列表末尾。
- `[融合]` 返回 `null`、空集合、`Optional` 或特殊对象取决于公开契约。默认选择让调用者最难误用的表达，并在边界上保持一致。
- `[强]` 公开接口特别是批量接口要校验数量、大小、范围和权限；私有热点方法可依赖已经明确建立的前置条件。

## 控制流

- `[强]` `if`、`else`、循环和传统 `switch` 分支使用大括号，避免后续修改改变控制范围。
- `[融合]` 传统 `switch` 明确终止或注释有意贯穿。现代 `switch` 表达式、枚举或密封类型若利用编译器穷尽检查，不要为了旧规约盲目增加 `default`。
- `[强]` 对可能为 `null` 的外部 `String` 执行 `switch` 前先处理空值。
- `[原则]` 优先用卫语句处理异常路径，减少多层 `if/else`；三层嵌套是审视设计的信号，不是硬性上限。
- `[原则]` 把复杂条件提取为能解释意图的布尔变量或方法；优先正向条件，避免双重否定。
- `[建议]` 不在条件或算术表达式中夹带赋值，不把昂贵且循环不变的操作重复放在循环体内。
- `[强]` 包装类型参与三目表达式时检查自动拆箱，避免空值触发异常。
- `[强]` 并发计数或库存退出条件不要依赖可能被越过的精确等值，应保证状态更新原子且边界条件可达。

## 副作用与错误

- `[原则]` 查询和命令尽量分开：一个方法要么回答问题，要么改变状态。确有必要组合时，通过名称和返回类型明确契约。
- `[原则]` 不隐藏时间顺序依赖。必须按顺序调用的步骤应由类型、对象状态或一个更高层方法表达。
- `[融合]` `try/catch` 只包住真正可能失败的操作，错误处理与正常业务路径分离；详细规则见 [exceptions-and-logging.md](exceptions-and-logging.md)。
