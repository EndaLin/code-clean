# Java 异常、错误码与日志

## 异常边界

- `[强]` 能通过清晰前置检查避免的输入错误，不用捕获运行时异常来做正常流程控制。
- `[原则]` 在能采取恢复、转换、补偿或补充上下文的层级捕获异常；否则继续传播。
- `[强]` 不吞掉异常。捕获后必须处理、转换并保留原因，或重新抛出。
- `[融合]` 捕获尽可能精确的异常类型。只在进程、任务或插件隔离等最外层边界考虑捕获 `Throwable`，并按平台策略处理致命 `Error`；不要把它作为普通 RPC 调用的默认写法。
- `[原则]` 异常信息包含失败操作、关键非敏感标识和上下文，保留原始 `cause`，不要只抛笼统的 `RuntimeException`。
- `[原则]` 异常类型按调用者可采取的动作设计，不按每个底层实现细节无限增殖。
- `[强]` 捕获类型必须覆盖实际抛出类型；不要用不相关异常掩盖编译或运行问题。

## 资源与事务

- `[融合]` 首选 `try-with-resources` 关闭流、连接、锁外资源等 `AutoCloseable` 对象；无法使用时在 `finally` 中可靠释放。
- `[强]` 不在 `finally` 中 `return`，避免覆盖正常结果或原始异常。
- `[强]` 显式锁在成功加锁后立即进入 `try`，并在 `finally` 解锁；尝试加锁时只在确认持有锁后释放。
- `[强]` 事务异常被捕获后，核对框架回滚规则；需要时显式标记回滚，不能返回成功掩盖部分提交。

## 空值与正常流程

- `[融合]` 默认使用类型、空集合、`Optional` 或特殊对象减少不必要的 `null`。若公开契约允许返回 `null`，必须明确说明并在边界处理；不要为了教条改变已有兼容契约。
- `[原则]` 不把异常情况伪装成普通返回码，也不让正常的“未找到”依赖昂贵异常；根据调用者语义选择表达。

## 错误码

- `[融合]` 对外协议要求错误码时，保持稳定、可搜索、可映射；错误码与面向用户的提示分离。
- `[强]` 不把内部错误码直接当用户文案，不在编码中塞入组织架构、版本或易变化业务信息。
- `[建议]` 转换第三方错误时保留原始系统、原始码和关联标识，避免排障信息丢失。
- 错误码位数和编码方案属于组织契约，不能把黄山版的五位格式强加给已有系统。

## 日志

- `[强]` Java 项目通过项目统一日志门面记录，不直接混用底层实现；无框架约定时优先 SLF4J。
- `[强]` 使用参数化日志，不用字符串拼接；昂贵参数或序列化前检查相应日志级别。
- `[强]` 生产代码不用 `System.out`、`System.err` 或 `printStackTrace()` 代替日志。
- `[融合]` 一次失败由最能处理或呈现它的边界记录一次。避免每层“记录后再抛”造成重复堆栈。
- `[强]` 需要记录异常时同时包含可行动的现场信息与异常对象，不能只打印 `exception.getMessage()`。
- `[强]` 不直接序列化整个业务对象到日志，避免性能、递归、体积和敏感信息风险。
- `[融合]` 密码、令牌、密钥、身份证件、联系方式、支付信息和其他个人数据必须删除或脱敏。
- `[原则]` 日志级别表达运维动作：预期业务拒绝通常不是 `error`；不可恢复失败不能被降为普通 `info`。
- 日志保存期限、文件名和合规策略由部署环境统一配置，不写死在业务代码中。
