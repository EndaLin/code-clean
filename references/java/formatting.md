# Java 格式与文件组织

## 权威来源

仓库已有格式化器、Checkstyle、Spotless、EditorConfig 或贡献规范时，以其为准。格式审查不应制造与功能改动无关的大面积差异。

## 无项目规范时的 Java 默认值

- `[强]` 使用 4 个空格缩进，不使用制表符；文本编码为 UTF-8，换行为 LF。
- `[强]` 关键字与左括号之间留空格，括号内部不额外留空格，二元和三元运算符两侧留空格，逗号后留空格。
- `[强]` 非空代码块的大括号和换行保持一致；空块只有在确实合理时写成 `{}`。
- `[强]` 单行默认不超过 120 个字符。换行要保持调用链、运算符和参数关系清楚。
- `[建议]` 不用额外空格纵向对齐赋值号；字段变化会让这种对齐产生无关修改。
- `[建议]` 用一个空行分隔不同概念，相关代码保持靠近，不连续堆叠多个空行。

## 可读顺序

- `[原则]` 文件像文章一样先给出高层意图，再逐步进入细节；调用者和被调用的私有方法保持可追踪的距离。
- `[原则]` 同一职责的重载、构造方法和辅助方法放在一起，但不要为了固定排序拆散一段自然的阅读流程。
- `[原则]` 一个源文件尽量只承载一种主要语言；嵌入 SQL、HTML、JSON 或脚本时，控制范围并提供清晰边界。
- `[融合]` 导入是否使用通配符由项目检查规则决定。Clean Code 的通配符偏好与现代 Java 项目常见规范不同，不能自动套用任一方。

## 修改原则

- 先运行项目已有格式化器，再检查无法自动表达的结构问题。
- 不把纯格式差异和行为修改混在大范围改动中，除非用户明确要求全量格式化。
- 方法 80 行、类大小或文件长度只用于触发职责检查，不单独作为缺陷证据。
