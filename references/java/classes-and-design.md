# Java 类、对象、边界与设计

## 类与职责

- `[原则]` 类应有一个清晰的变化原因。大小按职责数量、内聚性和依赖范围判断，不按行数机械判断。
- `[原则]` 字段和方法共同服务同一职责；只有部分方法使用一组字段时，考虑提取更内聚的类。
- `[融合]` 默认收紧可见性并保护不变量。为了测试放宽封装是最后手段，先考虑从公开行为测试或提取协作者。
- `[原则]` 优先组合而非继承。只有确实满足可替换关系且基类契约稳定时才使用继承。
- `[原则]` 基类不依赖具体派生类；高层策略依赖稳定抽象，具体实现放在边界。
- `[原则]` 对扩展开放、对无关修改关闭，但不要为了假想变化提前制造层层接口。

## 对象与数据结构

- `[原则]` 对象隐藏数据表示并提供行为；数据传输对象表达数据。不要同时暴露全部字段又塞入复杂业务行为形成混杂模型。
- `[原则]` 避免长串导航调用暴露内部结构。让拥有数据的对象完成相关行为，或在边界使用明确 DTO。
- `[原则]` DTO、记录类和持久化对象可以保持简单，但业务规则应有明确归属，不能散落在控制器、映射器和工具类中。
- `[原则]` 把边界条件、可配置数据和变化点集中到清楚的位置，不在各层重复相同判断。

## 系统边界

- `[原则]` 将对象构建、依赖装配和启动逻辑与运行时业务逻辑分开。
- `[原则]` 第三方库、远程 API 和尚未稳定的接口用小型适配层隔离；通过边界测试了解真实行为。
- `[原则]` 让依赖方向从易变细节指向稳定策略。跨层调用、事务和异常转换应有一致位置。
- `[原则]` 并发、持久化、鉴权、缓存等横切能力不应散落复制，但引入框架前要证明它带来实际价值。
- `[融合]` 先让测试通过，再用小步重构去重、表达意图和减少结构。避免没有保护网的整体重写。

## 设计审查尺度

- 单一职责、依赖倒置、开闭原则和设计模式用于解释具体变化风险，不作为“缺一个接口”或“模式不够多”的打分表。
- 只有当耦合已经导致重复修改、难以测试、错误传播或明确扩展阻塞时，才把结构问题列为缺陷。
- 图表在能澄清复杂状态、调用顺序或模型关系时使用；不要按对象数量阈值强制生产文档。
