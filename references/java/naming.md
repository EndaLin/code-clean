# Java 命名

## 判断目标

名称要让读者无需翻到实现即可理解“它是什么、为何存在、使用后会发生什么”。命名问题只有在造成误导、歧义、契约冲突或显著理解成本时才应作为缺陷；单纯偏好不同通常只是建议。

## 通用原则

- `[原则]` 使用能表达意图的名称，避免 `data`、`info`、`manager`、`process` 等无法说明职责的宽泛词，除非它们在领域中已有精确定义。
- `[原则]` 名称不得暗示错误的类型、单位、排序、线程安全性或副作用。例如返回无序集合却命名为 `sortedItems` 属于缺陷。
- `[原则]` 区分两个概念时给出业务差异，不用数字后缀、噪声词或近义词勉强区分。
- `[原则]` 名称应可读、可搜索。短循环索引可用 `i`，但跨越较大作用域的名称应更具体。
- `[原则]` 同一概念使用同一词汇；不要在同一代码库中混用 `fetch`、`get`、`load` 表示完全相同的动作。
- `[原则]` 类和数据类型通常用名词，方法通常用动词或动宾短语；布尔值使用能读成判断句的名称。
- `[原则]` 优先使用业务领域术语；实现机制确实重要时再使用算法、模式或协议等技术术语。
- `[原则]` 名称处于正确的抽象层级，不暴露可替换的内部实现，也不隐藏调用者必须知道的副作用。
- `[原则]` 避免双关、玩笑、私人缩写、难读的编码前缀和需要读者在脑中翻译的名称。
- `[融合]` 魔法值应替换为语义明确且作用域合适的常量；但 `0`、`1` 等在局部算法中含义显然的值不必机械抽取。

## Java 默认约定

- `[强]` 类名使用 `UpperCamelCase`；方法、参数、字段和局部变量使用 `lowerCamelCase`；常量使用语义完整的 `UPPER_SNAKE_CASE`。
- `[强]` 包名使用小写英文单词。单复数和层级首先服从项目已有约定，不为此进行大范围迁移。
- `[强]` 普通标识符不以下划线或美元符号开头或结尾，不混用拼音与英文，不使用侮辱性或歧视性词语。
- `[强]` 不使用无法辨认的缩写，不在父子类字段或相邻作用域中重复使用容易混淆的名称。
- `[融合]` 抽象类、异常类和测试类可采用项目通行后缀；`AbstractXxx`、`XxxException`、`XxxTest` 是默认值，不是覆盖仓库惯例的理由。
- `[融合]` POJO 布尔字段是否使用 `is` 前缀必须核对 JavaBeans、序列化框架、Lombok、记录类和数据库映射；不要只改一端。
- `[建议]` 枚举成员使用大写下划线；是否给枚举类型增加 `Enum` 后缀服从项目约定。
- `[建议]` 若接口表示能力，可使用 `-able` 等形容词；是否使用 `Impl` 后缀由项目架构决定，不能为了模式感制造无意义接口。

## 重命名边界

- 重命名前搜索反射、配置、表达式语言、JSON 字段、ORM 映射、模板、脚本和外部调用。
- 公开 API、数据库字段或消息字段的名称变更是兼容性变更，不能只按风格建议直接执行。
- 审查时给出更好名称只是建议；只有原名导致误用、与行为矛盾或违反明确项目规范时才升级为问题。
