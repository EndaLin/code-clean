# Java 注释与 Javadoc

## 注释应该补充代码无法表达的信息

- `[原则]` 首选通过名称、方法拆分和类型表达意图。注释不能补救混乱代码。
- `[融合]` 值得保留的注释包括：设计动机、业务约束、非显然的不变量、兼容性原因、安全警告、协议说明、法律声明和公开 API 契约。
- `[原则]` 注释解释“为什么”或“为什么不能采用看似简单的做法”，不要逐句翻译代码。
- `[原则]` 公共 API 的 Javadoc 要准确描述契约、参数限制、返回值、异常和副作用；私有实现不需要为满足数量而写空洞 Javadoc。
- `[融合]` 接口和抽象方法若契约不能从名称及类型清楚得出，应写 Javadoc。覆盖方法只在补充或改变契约时增加说明。
- `[强]` 枚举值承载外部可见或不直观业务含义时，应说明每个值的用途。

## 保持真实和局部

- `[强]` 修改参数、返回值、异常或核心逻辑时同步更新相关注释。
- `[原则]` 注释只描述附近代码负责的事实，不复制可能在其他模块变化的非本地信息。
- `[原则]` 错误或过期注释比没有注释更危险，应立即修正或删除。
- `[强]` 单行实现注释放在相关语句上方，`//` 后保留一个空格；多行说明使用项目统一格式。
- `[建议]` 使用团队能准确理解的语言，协议名、类型名和关键字保留标准写法。

## 应删除或避免的注释

- `[原则]` 删除重复签名或代码字面含义的注释、无信息的 Javadoc、括号结束标记和装饰性分隔符。
- `[原则]` 删除注释掉的旧代码；版本控制保存历史。若暂时保留必须有明确原因和清理条件。
- `[原则]` 作者、修改日期和变更日志应由版本控制维护，除非法律或仓库规范明确要求。黄山版“所有类添加创建者和日期”的规则不作为默认要求。
- `[原则]` TODO 应能追踪责任或任务，并定期清理；不要留下无限期占位承诺。
- `[原则]` 避免在注释中塞入大段 HTML、无关背景、署名或可由工具生成的信息。

## 审查尺度

把误导性注释、缺失的关键安全/协议约束和错误公开契约视为问题。仅缺少作者、日期或逐方法说明，不应在没有项目要求时报告为缺陷。
