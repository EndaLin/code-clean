# Go 测试

## 组织测试

- `[Go]` 修改 Go 代码后先让仓库规定的格式工具处理改动文件，再运行相关包测试；交付前运行仓库要求的全部模块测试、`go vet` 和已配置的静态检查。多模块仓库不要假设一次 `go test ./...` 会覆盖所有模块。
- `[Go]` 使用仓库既有的 `go test` 入口和构建标签。测试放在对应包的 `_test.go` 文件中；选择同包测试还是外部 `package_x_test`，取决于是否需要验证包外视角，不机械统一。
- `[Go]` 表驱动测试适合多个输入共享同一行为和断言的场景；只有一个场景或每个场景流程差异很大时，直接测试通常更清楚。
- `[Go]` 子测试名称描述场景并保持唯一。只有测试不共享全局状态、环境变量、端口、临时资源或不可并发的 fixture 时才调用 `t.Parallel()`。
- `[Go]` 测试帮助函数调用 `t.Helper()`；资源使用 `t.Cleanup()`、`t.TempDir()` 等生命周期工具。不要为清理失败吞掉会改变测试结论的错误。

## 验证行为

- `[融合]` 断言公开行为、边界和错误语义，不绑定内部调用次数或私有结构，除非那些细节就是契约。
- `[Go]` 错误断言使用 `errors.Is`、`errors.As` 或稳定字段，不比较会随上下文变化的完整错误字符串；确需验证文案时只锁定对外承诺部分。
- `[Go]` 并发测试使用明确同步和截止时间，避免只靠 `time.Sleep`。对共享状态和 goroutine 生命周期运行 `go test -race`，并确保测试实际走到相关路径。
- `[Go]` fuzz test 用于解析器、编解码、边界输入和不变量等适合自动探索的代码；保存最小回归样本，并保持结果可重复。
- `[Go]` `Example` 测试适合同时提供可执行文档；基准测试只在性能是需求且环境、输入、分配统计可解释时使用。

## 外部边界

- `[融合]` 单元测试不能证明真实数据库、文件系统、远程 API 或消息系统可用。声称集成可用前，必须运行命中对应真实边界的最小测试，并保留不含凭证的结果标识和失败原因。
- `[Go]` 测试默认不依赖公网、真实时钟、随机顺序或机器已有数据。确属集成测试时显式区分运行入口、前置条件和清理策略。
- `[Go]` golden 文件的更新必须是显式操作，审查差异后提交；不能在普通测试运行中自动把当前错误输出覆盖成期望值。
