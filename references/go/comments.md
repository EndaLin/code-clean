# Go 注释与公开文档

## 文档注释

- `[Go]` 每个包都应有包注释；多文件包通常只写一处。包注释说明包提供什么、重要边界和调用者需要知道的限制。
- `[Go]` 导出的类型、函数、方法、变量和常量应有紧邻声明的文档注释。第一句使用完整句子并以被说明的名称开头，便于 `go doc` 和 `pkg.go.dev` 展示与搜索。
- `[Go]` 文档描述调用者可观察的契约：返回结果、副作用、特殊情况、错误语义、零值行为，以及类型是否可被多个 goroutine 安全使用。不要泄露无关实现步骤。
- `[Go]` 导出结构体字段的语义必须能从类型文档或字段注释中得知。单位、范围、是否可空、所有权和并发约束不能靠猜。
- `[Go]` 包级示例适合写成可执行的 `Example` 测试，让文档与代码一起校验；不要用无法运行的大段示例替代测试。

## 普通注释

- `[融合]` 解释选择原因、不变量、所有权、取消条件、协议限制和看似多余但不可删除的兼容逻辑。不要逐行翻译代码。
- `[Go]` 行注释是常用形式。让 `gofmt` 处理文档段落、列表、链接和代码块，不用装饰性横幅或原始 HTML 模拟排版。
- `[Go]` `Deprecated:` 段落用于真实的弃用契约，并给出替代方案。`//go:`、`//line` 等工具指令不是普通说明文字；只有理解工具语义且任务确实需要时才修改。
- `[融合]` TODO、BUG 和静态检查抑制应包含仓库要求的责任人、任务号或理由，并保持最小范围。临时抑制不能掩盖真实错误。
- `[融合]` 修改公开行为、错误、并发保证或零值语义时同步更新文档；无法确认注释是否仍真实时，不把猜测写成事实。

## 审查尺度

缺失或错误的公开契约、错误的并发安全声明、过期的指令和会导致误用的注释属于问题。没有为显然的私有代码补注释通常不是缺陷。
