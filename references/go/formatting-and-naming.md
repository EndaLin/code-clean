# Go 格式与命名

## 先确认版本和工具

- `[Go]` 先读 `go.mod`、`go.work`、工具链声明、静态检查配置和仓库约定。语言版本会影响可用语法与语义，不能只看本机安装的 Go 版本。
- `[Go]` 以 `gofmt` 的结果为格式基准；仓库使用 `goimports` 或其他导入整理工具时，服从其配置。不要手工维持与工具冲突的对齐方式。
- `[Go]` 不手写分号，不给 `if`、`for`、`switch` 条件加多余括号，左花括号与声明或控制语句放在同一行。
- `[Go]` Go 没有统一的硬性行宽。行过长时优先调整表达式或局部结构，不靠压缩名称和堆叠缩写解决。

## 包与文件

- `[Go]` 包名简短、小写、单数且能说明职责，通常不使用下划线或 MixedCaps。避免 `util`、`common`、`misc` 等无法形成清晰边界的名称。
- `[Go]` 从调用处审视名称，避免包名与导出名重复，例如优先让调用读成 `http.Server`，而不是同义词反复出现。
- `[Go]` 只在冲突或显著提升理解时使用导入别名。点导入会隐藏来源，默认避免；空白导入只用于明确需要的注册副作用，并在不显然时说明原因。
- `[Go]` 文件名和文件拆分服从仓库约定。不要仅因文件较长就机械拆分，应按职责、平台构建条件或可理解边界组织。

## 标识符

- `[Go]` 标识符使用 `MixedCaps` 或 `mixedCaps`，不使用下划线分词。首字母大小写决定包外可见性，重命名前必须检查公开 API 兼容性。
- `[Go]` 缩写在同一名称中保持一致，例如项目选择 `URL`、`ID` 后，不要在相邻 API 中混用 `Url`、`Id`。已有公开名称不为统一风格轻易破坏兼容性。
- `[Go]` 小作用域可使用 `i`、`r`、`ctx` 等惯用短名；作用域越大、同类值越多，名称越需要表达差异。不要把所有变量都扩成冗长句子。
- `[Go]` getter 通常直接命名为 `Owner()` 而非 `GetOwner()`；确有 setter 时可命名为 `SetOwner()`。名称仍须准确表达计算、阻塞和副作用。
- `[Go]` 单方法接口仅在自然表达能力时使用 `-er` 名称，如 `Reader`。不要为了后缀制造接口，也不要让接口名复述所在包名。
- `[Go]` 方法接收者使用类型名的一两个字母缩写，并在该类型的方法间保持一致；不使用 `this`、`self`、`me`。
- `[Go]` 导出的错误值通常用 `ErrXxx`，导出的错误类型通常用 `XxxError`。只有调用者确实需要识别时才导出。

## 审查尺度

格式差异应优先交给工具修复。只有名称造成误导、可见性泄露、包职责含混或违反仓库明确约定时才报告为问题；纯粹的缩写偏好列为建议。
